Observed triggerabout 144 or more requests per minute with no failed logins (measured on the committed model)

Decision order inside the AMF from the code

  1. Check the slice against the allowlist. If not allowed: HTTP 403 unauthorized slice, increment blocked. Nothing else runs.
  2. Count this UE's requests and failures in the last 60 seconds.
  3. Ask the model. If anomalous: HTTP 403 blocked_by_ai, increment threat and blocked counters, append to alerts.log.
  4. Authenticate at AUSF, create the session at SMF, register at NRF, reply 201.

Architecture and data flow drawn from the code

Four diagrams, drawn from core/amf.py, the Service and Deployment files, prometheus.yml and the Jenkinsfile. They describe the design; they are not live data.

How to explain it

  1. Left: the UE sends a registration request; the operator reads alerts.log; Jenkins deploys the pods.
  2. Inside the AMF (P1): slice allowlist, count requests, AI check, then orchestrate. Each failed check returns a 403, 401 or 500 to the UE.
  3. The AMF calls AUSF (5002), SMF (5003) and NRF (5001) over mutual TLS, using certificates from certs/.
  4. Right: Prometheus pulls /metrics every 5 s from all four functions and Grafana reads Prometheus. Only AI blocks are written to alerts.log.

How to explain it

How to explain it

  1. Slice check first: a slice outside slice-a/slice-b gives 403 unauthorized slice (counted, not logged, and no per-slice state is created).
  2. AI check second: an anomaly (-1) gives 403 blocked_by_ai, counters go up and a line is written to alerts.log.
  3. Between the two checks the AMF counts this UE+slice's requests and failures over the last 60 seconds. Then AUSF, SMF and NRF in order. An AUSF failure gives 401 and is remembered for the next AI check.

How to explain it
